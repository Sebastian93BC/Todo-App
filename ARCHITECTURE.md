# Architecture Overview

This document describes the high-level structure and data flow of the Todo App.
It complements the README and DEVELOPMENT guides by focusing on architectural
concepts rather than setup instructions or implementation details.

## Components

The application consists of two main components:

1. **Frontend (client)**
   - **Files:** `index.html`, `script.js`, `style.css`
   - **Purpose:** Provide a responsive user interface for creating and managing
tasks. Operates in the browser and is intentionally framework-free (vanilla
JavaScript) for simplicity.
   - **Features:**
     - Local state management using a `todos` array
     - Multiple filter options (state, category)
     - Inline editing and state cycling
     - Light/dark theme toggle
     - Offline-first design with localStorage persistence
     - Synchronization logic to communicate with the backend

2. **Backend (server)**
   - **Files:** `server/index.js` plus supporting files (`package.json`, etc.)
   - **Purpose:** Host a RESTful API backed by SQLite to act as centralized
storage for tasks. Allows multiple browsers or devices to share the same data.
   - **Tech stack:** Node.js with Express, `better-sqlite3` for database access.
   - **Key capabilities:**
     - Create, read, update, delete tasks
     - Bulk sync and one-time migration endpoints
     - Health check
     - CORS enabled to permit cross-origin requests


## Data Model

Tasks ("todos") are represented by a simple object with the following fields:

- `id` (number): unique identifier (timestamp-based when generated on client)
- `text` (string): task description
- `state` ("plan" | "todo" | "done"): workflow state
- `category` ("trabajo" | "personal" | "estudio"): classification
- `created_at` / `updated_at` (server only): timestamps generated by SQLite

The client object mirrors the server schema except for timestamps, which are
added server-side.

## Data Flow and Synchronization

1. **Load**: On startup, the client calls `loadTodosFromServerOrLocal()`.
   - If the server responds, the returned list becomes the working state and
     localStorage is updated.
   - If the server is unreachable, the client falls back to localStorage.
   - During the first successful server interaction, the client may trigger a
     one-time migration of any existing localStorage data via
     `POST /api/migrate`.

2. **User actions** (add, edit, delete, state change, category change) update
the `todos` array. Each action invokes `saveTodos()`.

3. **saveTodos()**
   - Immediately writes the full `todos` array to localStorage.
   - Attempts to `POST /api/sync` with the complete array.
   - If sync fails (server down or network issue), a flag
     `needsSync` is set and the client schedules retries every 10 seconds.
   - Once a sync succeeds, `needsSync` is cleared.

4. **Offline resilience**: The app remains fully usable when offline; all
   state updates persist locally and queue for later sync.

## Synchronization Strategies

- **Full sync (`/api/sync`)**: Client sends the entire task list. The server
deletes all existing records and replaces them with the supplied array. This
simplifies conflict resolution at the cost of more bandwidth, but the small
payloads in this app make it acceptable.

- **Migration (`/api/migrate`)**: One-shot import of tasks from the client
localStorage to an empty server. The endpoint rejects subsequent calls if the
server already contains data (409 conflict).

- **Per-item endpoints**: Used internally by the server for individual CRUD
operations but not directly invoked by the client in the current implementation
(with the exception of health checks and potentially future extensions).

## Offline/Online Detection

The client maintains a boolean `serverAvailable`. Network requests time out
using a configurable `SERVER_TIMEOUT` (default 5000 ms). Failure to connect
disables sync attempts until a later retry.

Periodic health-check pings (`/api/health`) could be added to detect server
availability proactively; currently retry logic is tied to failed syncs.

## Deployment Considerations

- The frontend can be hosted as static files anywhere (GitHub Pages, S3,
etc.). It needs to be configured to point `API_URL` at the deployed backend.
- The backend runs on Node.js and requires either local SQLite or a hosted
SQLite-compatible service. In production, port and CORS origin should be
locked down via environment variables.

## Extensibility

The codebase is intentionally small; features such as user accounts,
real-time collaboration, or plugin support would require introducing a database
migrations system, authentication, and a richer client framework. However, the
existing architecture clearly separates concerns and can serve as a foundation
for incremental growth.
